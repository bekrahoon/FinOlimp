# Сверка 1С ↔ ETM: инструкция бухгалтеру (1 страница)

## Установка и запуск из корня проекта

На новом компьютере выполните установщик один раз:

- Windows PowerShell: `powershell -ExecutionPolicy Bypass -File .\install_windows.ps1`
- Ubuntu: `bash install_ubuntu.sh` (потребуется `sudo` для `apt`).

Для запуска Stage 1 + Stage 2:

```text
Windows: .\.venv\Scripts\python.exe .\run_stage_1_2.py
         .\.venv\Scripts\python.exe .\run_ai.py
Ubuntu:  .venv/bin/python run_stage_1_2.py
         .venv/bin/python run_ai.py
```

Каждый запуск пишет результаты в новую `.finolimp/manual_runs/<run-id>/` и
сохраняет манифест с SHA-256 входных файлов; существующие отчёты не меняются.
На Ubuntu завершённый каталог запуска закрывается для других пользователей и
становится доступен только для чтения.
Книги `finolimp_reports.xlsx` и `README.xlsx` лежат в `stage1/`; ML CSV — отдельно
в `stage2/` и не смешиваются с бухгалтерской книгой Stage 1. Stage 2 сам создаёт
`stage2/train/` из текущих входов и Stage 1, выполняет bootstrap, добавляет source-метки
из отчёта Stage 1, обучает модели и записывает ML-результаты. Замороженные train CSV
Stage 2 не используются; таблицы строятся заново для каждого запуска.

По умолчанию последние 20% уникальных дат выгрузок выделяются в chronological
validation, предыдущие даты — в train. Пары через границу исключаются. Параметр
`--validation-fraction` меняет долю validation, например `--validation-fraction 0.25`.
Для ровной помесячной границы используйте `--validation-months N`: validation —
последние N полных календарных месяцев (например, `--validation-months 2` на
данных январь–июль даёт экзамен июнь–июль с cutoff 2026-06-01).
Отчёты показывают метрики отдельно на отложенных датах.

Важно: метки для обучения и validation производны от решений Stage 1 («silver»).
Хронологическая validation не участвует в fit, но не является независимой
человеческой проверкой правильности Stage 1;
основным бухгалтерским результатом остаётся Stage 1. Если в ранний train-fold не
попали сопоставленные source-метки Stage 1, source-модель будет пропущена с
предупреждением; остальные модели Stage 2 выполняются.

Чтобы запустить только Stage 1, добавьте `--stage1-only`. Stage 2 отдельно запускается
из входов и отчётов ранее завершённого Stage 1:

```text
Windows: .\.venv\Scripts\python.exe .\run_stage_1_2.py --stage2-only --stage1-reports <путь-к-stage1>
Ubuntu:  .venv/bin/python run_stage_1_2.py --stage2-only --stage1-reports <путь-к-stage1>
```

В per-run CSV технические заголовки сохраняются, а значения `check` и `issue`
заменяются русскими пояснениями. Для AI запустите `run_ai.py` тем же Python:
откроется OpenCode в
папке `stage3_ai`. Он не начнёт сверку сам; сначала подключите провайдера через
`/connect`, если это первое использование, и отправьте запрос в чате.

## Запуск (раз в месяц, на новых выгрузках)
Требуется: Python 3, пакеты `pandas pyyaml`
(`pip install pandas pyyaml`). Этап 1 — только правила, ML-зависимостей нет
(scikit-learn нужен лишь этапу 2).

```bash
cd finolimp/stage1_rules/src
python3 match.py --input ../input --out ../reports
```

`--input` — папка с тремя файлами: `acts.csv`, `etm.csv`, `registry.csv`
(лежит в `stage1_rules/input/`).
`--out` — куда положить отчёт (создастся сама).

## Что выходит (`report/`)
| Файл | Что делать |
|---|---|
| `discrepancies.csv` | Главный список расхождений: агент, дата, билет/документ, суммы, разница, пояснение, **source** (где ошибка: бот / 1С / агент / выяснить) |
| `agent_actions.csv` | Поручения на субагента одной строкой: `move_etm_by` — изменение баланса ETM, `fix_1c_by` — изменение сальдо 1С, `clarify_money`/`clarify_n` — сначала выяснить (деньги/штуки). Знак в обеих колонках: плюс — увеличить баланс/сальдо, минус — уменьшить |
| `agent_risk.csv` | Порядок обхода субагентов: сначала большие старые суммы (`old_money_30d`), потом плотные по ошибкам; свежие (≤31 дня) — в конце, они часто сами расходятся |
| `employee_risk.csv` | Авторы реестра: `suspect_rows` — его цифры под вопросом, `witness_rows` — его записи верны (доказательство чужой ошибки), `total_rows` — все строки реестра этого автора, `suspect_rate` — доля подозрительных от полного знаменателя |
| `reconciliation_summary.csv` | Сходимость по каждому субагенту (`residual` должен быть 0) |
| `quality_report.csv` | Технические пометки движка (пропуски загрузки, дубли, сироты реестра) |
| `review_candidates.csv` | Отдельная очередь на ручную проверку: блоки месяцев без актов, void в реестре без void в ETM, возможный FX-сдвиг. Кандидаты не меняют `source` и не являются готовыми проводками |
| `label_map.csv` | Как одно и то же имя пишется в разных файлах (САЛАМ ЭЙР = ОсОО «Салам Эйр») |
| `features.csv` | Технические признаки строк (для аналитика, не для обхода) |

## Как читать `source`
- **бот** — бот не загрузил строку реестра, задвоил или занизил ETM (реестр сошёлся с 1С): чинить загрузку, строку сверить.
- **1С** — операция реальна (ETM + реестр сошлись), в учёте её нет: довнести в 1С.
- **агент** — сумма реестра сошлась с ETM, а не с 1С (бот скопировал добросовестно): ошибка в учёте агента, спрашивать агента.
- **выяснить** — суммы разошлись (часто комиссии) или платёж с одной стороны: смотреть первичку.
  Подвид: в реестре продажа + сторно на следующий день — сначала выяснить валидность сторно.

## Правила, которые надо знать
1. Свежие расхождения (последний месяц выгрузки, ≤31 дня) — чаще лаг, чем ошибка: сначала старые.
2. Круглые разницы (1000 / 9000 / 10000, ровно 5% / 10%) — подпись опечатки или удержания: в первичку.
3. Самовыписки субагента (в реестре их нет по построению) — спрашивать субагента + довносить в 1С.
4. `residual != 0` в summary — баланс не сошёлся: смотреть `quality_report.csv`, звать автора инструмента.
5. Войды: движок проверяет, что каждый войд полностью закрыл свои продажи
   (`void_partial_refund` в quality; сейчас 0). Появление строк там — разбирать первым.

## Новый месяц (rollover): что делать
1. Положить свежие `acts.csv`, `etm.csv`, `registry.csv` в новую папку, запустить
   `match.py --input <папка> --out report_<месяц>/`. Ничего в настройках менять
   не надо: конец выгрузки (`data_end`) определяется сам как максимальная дата.
2. Проверка, что отчёт живой: все `residual` в summary — 0; `pytest tests/ -q` —
   зелёный на синтетике. **md5-гейты тестов привязаны к июльским данным** —
   на новых данных они покраснеют, это нормально (данные другие, не поломка).
3. Если в новом месяце `data_end` надо зафиксировать вручную (частичная выгрузка) —
    задать `v3.data_end: "2026-08-31"` в копии `reconcile.yaml` и передать её
    флагом `--config`.

## Stage 2 результаты и Excel

Все train-файлы, bootstrap-артефакты, ML-отчёты и прогнозы конкретного запуска
находятся в `.finolimp/manual_runs/<run-id>/stage2/`. Главный файл —
`stage2_discrepancies_ml.csv`; метрики и provenance моделей —
`stage2_inference_report.json`; построенные таблицы и описание меток —
`train/training_report.json`. Stage 2 не меняет CSV Stage 1 и не смешивается с
бухгалтерской книгой.

Для каждого завершённого запуска Stage 1 отдельно создаются `stage1/finolimp_reports.xlsx`
на основе CSV этого запуска и `stage1/README.xlsx` — словарь полей. CSV-заголовки
сохраняются; переводятся только значения `check` и `issue`. Книги разных запусков
не объединяются.

## OpenCode: режим «Сверка»

В корне проекта открыть OpenCode V2 и выбрать агента **Reconcile**. MCP-инструменты
используют только три фиксированных файла из `stage1_rules/input/`; агент создаёт
их snapshot, проверяет формат, запускает полный Stage 1 bundle и показывает отчёты.
Результаты пишутся в отдельные каталоги `.finolimp/runtime/` — исходные выгрузки и
предыдущие запуски не перезаписываются.

Для первого запуска нужны `uv` и Python 3.11+; зависимости MCP/pandas/PyYAML
установятся из `integrations/finolimp_mcp/pyproject.toml`. Проверки разработчика:

```bash
cd integrations/finolimp_mcp
uv sync --group dev
uv run pytest -q
uv run pytest -q ../../stage1_rules/src/tests
```

Этот срез пока не загружает выгрузки из чата, не запускает отдельные шаги и не
публикует улучшения. Кандидаты на ручную проверку остаются отдельными от `source`;
отчётные поручения не являются автоматически проведёнными операциями. Перед
передачей MCP-инструменту конфиденциальных данных проверьте локальную политику
хранения и доступа к `.finolimp/runtime/`.
