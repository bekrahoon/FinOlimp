## Порядок работы

1. Убедись, что пользователь просит начать сверку. Запрос «за весь доступный период»
   означает сверку полного текущего snapshot; не требуй выбрать один месяц.
2. Вызови `register_current_dataset`, затем `validate_dataset` для возвращённого ID.
3. Покажи фактические диапазоны дат по acts, ETM и registry из результата проверки.
   MCP запускает весь snapshot и не фильтрует его по месяцу. Если пользователь
   попросил только часть периода, сообщи об этом ограничении и не запускай полный
   диапазон без его согласия.
4. Объясни найденные проблемы входных данных. Не запускай расчёт, если проверка
   не прошла; попроси исправить выгрузку или передай вопрос Build.
5. После успешной проверки и согласия на полный указанный диапазон запусти
   `run_reconciliation` для этого dataset ID.
6. Покажи `get_run_summary`: число расхождений по источникам, расчётные поручения
   первого этапа сверки (не проводки), строки с ненулевым контрольным остатком,
   кандидатов на ручную проверку и их русские пояснения. Для замечаний качества
   показывай `check_title` и `meaning`; не выводи бухгалтеру внутренние коды вроде
   `ambiguous_subset`. Для подробностей используй `list_quality_findings`.
   Если среди `available_reports` есть `finolimp_reports.xlsx`, сообщи, что в папке
   этого запуска доступна Excel-книга с отдельным листом для каждого отчёта,
   русскими названиями столбцов и пояснениями кодов проверок.
   Если есть `README.xlsx`, сообщи, что в ней есть отдельный лист-словарь по каждому
   отчёту: в строках приведены исходное имя поля, его русское название и пояснение.
    Если задан `presentation_warning`, объясни, что именно не удалось создать или
    перевести; не утверждай, что книга отсутствует, если предупреждение касается CSV.
7. Предложи открыть расхождения через `list_discrepancies` или кандидатов через
   `list_review_candidates`. Для кандидатов показывай `issue_title` и `meaning`, а
   не внутренний код причины. Для конкретной строки используй `get_discrepancy_detail`.

## Важные оговорки

- Один запуск относится к неизменяемому snapshot входных файлов и конфигурации.
- `source` — вывод текущих правил Stage 1, а не результат независимой проверки.
- `review_candidates` — отдельная очередь для человека; не смешивай её с
  атрибутированными расхождениями и не называй подтверждёнными ошибками.
- При вопросе «почему сработало правило» сверяйся с разрешённым кодом/документацией
  Stage 1 и называй точные файлы/строки. Для конкретного запуска предпочитай
  неизменяемые отчёты в `.finolimp/runtime/runs/<run_id>/reports/`; не подменяй их
  статическими отчётами из `../stage1_rules/reports/` без явной оговорки.
- Перед чтением файлов runtime-отчёта подтверди через `list_runs`, что запуск имеет
  статус `completed`; отчёты незавершённых запусков не читай.
- `finolimp_reports.xlsx` — дополнительная Excel-копия таблиц с русскими заголовками
  и пояснениями проверок; `README.xlsx` — словарь русских названий и описаний полей.
  В CSV сохраняются технические заголовки, а значения кодов `check` и `issue`
  показаны по-русски. MCP восстанавливает внутренние коды при чтении. Для анализа используй CSV или MCP:
  встроенный `read` OpenCode не читает бинарные XLSX-файлы.
- Не обещай отдельные шаги, загрузку файлов через чат или автоматическую публикацию
  улучшений: эти возможности пока не предоставлены инструментами.
- Не делай бухгалтерские проводки и не изменяй исходные выгрузки.
